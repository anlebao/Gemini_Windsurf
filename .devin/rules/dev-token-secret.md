# DEV-TOKEN SECRET — SAFE USAGE (SECURITY RULE)

> **Scope:** `DevToken__Secret` / `DEV_TOKEN_SECRET` — the secret that gates
> `POST /api/customer-identity/dev-token` (ShopERP, forwarded by Gateway).
> **Applies to:** any agent or human enabling the endpoint for RV / testing on a real VPS.
> **Related:** `docs/AI/tasks/community_commerce_fixes/task_card_04_dev_otp_gate.md`

## 1. What it is

`POST /api/customer-identity/dev-token` mints a **365-day customer token** for a phone number,
skipping the SMS OTP flow. It exists so RV scripts can authenticate a test customer
(SMS OTP is not configured in production, and Google OAuth needs a real browser).

| `DevToken:Secret` | Endpoint behaviour |
|---|---|
| empty / unset | **404** (disabled) — this is the required production state |
| set, wrong `X-Dev-Secret` | 401 |
| set, correct `X-Dev-Secret` | 200 + long-lived token |

**Threat:** anyone who learns the secret can mint a token for **any phone number** and act as that
customer (orders, loyalty, community, chat). Treat the secret like a production credential.

## 2. HARD RULES

1. **Default = OFF.** The endpoint must be disabled (`DevToken:Secret` unset → 404) at all times
   except during an active RV window.
2. **NEVER commit a real secret** to the repo, a task card, a commit message, or this rule file.
   `.env.shoperp` is generated by CD from scratch — `DEV_TOKEN_SECRET` is deliberately **not** one
   of its inputs, so a committed value would never reach production anyway.
3. **NEVER persist the secret in `.env.shoperp`.** Pass it as an **inline shell env var** on the
   `docker compose up` command only. This makes the next CD deploy clear it automatically
   (CD rewrites `.env.shoperp` without `DEV_TOKEN_SECRET`).
4. **Never echo the secret** into agent output, logs, or the conversation. Write it to a
   `chmod 600` file on the VPS and read it back into a shell variable when needed.
5. **Always remove it at the end of the RV window** (section 4) and **verify** the removal
   (section 5). Do not leave it for "the next session".
6. **Never modify repository security policy or CI/CD config** to work around a failure — escalate.
7. Tokens already minted stay valid after the secret is removed (they are `IDataProtector`-based
   and independent of the secret). If a token leaked, removing the secret is **not** enough —
   the DataProtection key ring must be rotated.

## 3. ENABLE (temporary — RV window only)

```bash
# on the ShopERP VPS (vanan-shop-a), as the docker-capable user
cd /opt/vanan
SECRET=$(openssl rand -hex 32)
printf '%s' "$SECRET" > ~/.devtoken_rv_secret && chmod 600 ~/.devtoken_rv_secret

# inline env var ONLY — do NOT write it into .env.shoperp
DEV_TOKEN_SECRET="$SECRET" docker compose -f docker-compose.shoperp.yml \
  --env-file .env.shoperp up -d --force-recreate shoperp
```

Then verify it is live (`1` = set) and mint the test token:

```bash
docker exec vanan-shoperp-1 sh -c 'env | grep -c "^DevToken__Secret=.\+"'   # expect 1

curl -s -X POST https://api2.<domain>/api/customer-identity/dev-token \
  -H "X-Dev-Secret: $SECRET" -H 'Content-Type: application/json' \
  -d '{"phoneNumber":"+8490..."}'
```

Use the returned `customerToken` as `X-Customer-Token`. **Prefer an existing test customer** whose
phone is already known — the endpoint creates a customer if the phone is unknown.

## 4. DISABLE (mandatory — immediately after the RV window)

```bash
cd /opt/vanan
rm -f ~/.devtoken_rv_secret
docker compose -f docker-compose.shoperp.yml --env-file .env.shoperp up -d --force-recreate shoperp
```

A CD deploy also clears it (it rewrites `.env.shoperp` without the variable) — but do not rely on
that; remove it explicitly.

## 5. VERIFY REMOVAL (must all pass)

```bash
docker exec vanan-shoperp-1 sh -c 'env | grep -c "^DevToken__Secret=.\+"'   # expect 0
curl -o /dev/null -w '%{http_code}\n' -X POST \
  https://api2.<domain>/api/customer-identity/dev-token \
  -H 'X-Dev-Secret: anything' -H 'Content-Type: application/json' \
  -d '{"phoneNumber":"+8490..."}'                                          # expect 404
ls ~/.devtoken_rv_secret                                                  # expect "No such file"
```

Also delete any local temp files holding the token (`rv_token.txt`, etc.).

## 6. REPORTING

Every use must be recorded so the window is auditable:
- Add a dated line to the "TEMPORARY DEV-TOKEN SECRET" section of
  `docs/AI/tasks/community_commerce_fixes/task_card_04_dev_otp_gate.md`.
- State the enable/disable/verify results in the session summary.
- If removal verification fails, treat it as an **incident**: report immediately, do not continue
  with other work until the endpoint returns 404.
