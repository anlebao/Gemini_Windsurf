## 1. Use Case & Business Design

**Problem:**
Currently `OrderService.ConfirmPaymentAsync` (CoreHub) runs in both Gateway (PG) and ShopERP (SQLite) hosts. When KhachLink payment webhook hits Gateway, accounting entries are created in **Gateway PostgreSQL**. When POS staff confirms payment in ShopERP, entries are created in **ShopERP SQLite**. This dual-write creates:

1. **Split accounting truth** — same tenant's entries scattered across 2 databases.
2. **E-invoice complexity** — e-invoice integration (Viettel/MISA) only exists in ShopERP (`einvoice` module, `MisaConfig:BaseUrl` HTTP client). Gateway has no e-invoice code. Orders paid via KhachLink webhook never get e-invoices.
3. **Audit difficulty** — accountant must check 2 databases to reconcile.

**Decision (user-approved 2026-07-18):**
- **Accounting entries created ONLY in ShopERP SQLite.**
- Gateway webhook calls `OrderService.MarkPaidAsync` (sets status Paid in PG + enqueues `OrderPaymentConfirmed` Outbox event), does NOT create accounting entries.
- ShopERP subscriber receives event → sets status Paid in SQLite + creates accounting entries → enriches with e-invoice.
- E-invoice result syncs back to PG (so Gateway admin can view status).

**Flow (new):**
```
KhachLink payment → Gateway WebhookController
  → OrderService.MarkPaidAsync (PG: status=Paid, enqueues OrderPaymentConfirmed event)
  → Outbox → NatsSyncWorker → subject: vanan.cloud.order.payment.confirmed.{shopInstanceId}
  → NATS → ShopERP PaymentConfirmedSubscriber
    → Load order from SQLite
    → If not yet Paid: order.ConfirmPayment(transactionId, paymentMethod)
    → OrderService.GenerateAccountingEntriesAsync (SQLite)
    → If EInvoice_Auto_Export_Enabled: EInvoiceService.SubmitAsync
    → Enqueue Outbox event `EInvoiceSynced` (routing key = shopInstanceId) → NatsSyncWorker publishes `vanan.shoperp.einvoice.synced.{shopInstanceId}`
  → Gateway EInvoiceSyncSubscriber → update PG ElectronicInvoice table
```

**Out of scope:** QR code changes (Phase 5), FeaturedProduct (Phase 6), migration of existing PG accounting entries (separate task card if needed).

## 2. Reverse Impact Analysis

### Domain Layer (`1_Shared/`)
- **NO Domain modification** — `Order.ConfirmPayment()` domain method stays. Only the *service orchestration* changes (what happens after ConfirmPayment).
- `AccountingEntry` immutability preserved — entries still created once, append-only.

### CoreHub Services (`3_CoreHub/Services/`)
- **`OrderService.cs`** — SPLIT `ConfirmPaymentAsync` into 3 public methods:
  - `MarkPaidAsync(orderId, tenantId, transactionId, enqueuePaymentConfirmedEvent = false, cancellationToken)` — sets `order.ConfirmPayment()` + saves. If `enqueuePaymentConfirmedEvent = true`, enqueues `OrderPaymentConfirmed` Outbox event. **No `GenerateAccountingEntriesAsync` call.** SignalR broadcast `NotifyPaymentConfirmedAsync` is called here (customer sees "Paid" immediately).
  - `GenerateAccountingEntriesAsync(Order order, TenantId tenantId)` — **change from `private` to `public`** so `PaymentConfirmedSubscriber` can call it. Generates revenue + COGS entries for the provided (already Paid) order.
  - `ConfirmPaymentAsync(orderId, tenantId, transactionId, cancellationToken)` — **backward-compat wrapper** for POS and existing callers. Calls `MarkPaidAsync(..., enqueuePaymentConfirmedEvent: false)` then `GenerateAccountingEntriesAsync(...)`.
- **`OrderNotificationService.cs`** — `NotifyPaymentConfirmedAsync` SignalR broadcast stays in `MarkPaidAsync` (customer sees "Paid" immediately).

### Gateway (`2_Gateway/`)
- **`WebhookController.cs`** — change `ConfirmPaymentAsync` → `MarkPaidAsync`:
  - Line 160: `await _orderService.MarkPaidAsync(request.OrderId, request.TenantId, request.TransactionId, enqueuePaymentConfirmedEvent: true, cancellationToken);`
  - Response message: `"Payment confirmed. Accounting entries will be generated by ShopERP."` (acknowledges async nature).
- **Outbox event** — new event type `OrderPaymentConfirmed`:
  - Payload: `{ orderId, tenantId, transactionId, paymentMethod, paidAt }`
  - `paymentMethod` taken from `order.PaymentMethod ?? PaymentMethodConstants.Cash`.
  - NATS subject: `vanan.cloud.order.payment.confirmed.{shopInstanceId}` (produced by `NatsSyncWorker.BuildSubject("OrderPaymentConfirmed", "cloud")` + routing key `.{shopInstanceId}`).
  - Routed by ShopInstanceId (same as Phase 3 `OrderCreated` routing).
- **NEW: `EInvoiceSyncSubscriber.cs`** — subscribes to `vanan.shoperp.einvoice.synced.{shopInstanceId}`:
  - Payload: `{ orderId, tenantId, invoiceId, providerInvoiceNumber, status, submittedAt }`
  - Updates/creates `ElectronicInvoice` row in PG.
  - Idempotent: check if invoice already exists before insert.

### ShopERP (`5_WebApps/ShopERP/`)
- **NEW: `PaymentConfirmedSubscriber.cs`** — hosted service, subscribes to `vanan.cloud.order.payment.confirmed.{shopInstanceId}`:
  - Parse payload: `{ orderId, tenantId, transactionId, paymentMethod, paidAt }`.
  - Retry loop: load order from SQLite (should already exist via `OrderSyncSubscriber`); if not found, retry up to 5 times with 2s delay, then dead-letter log.
  - If order `PaymentStatus != "Paid"`: call `order.ConfirmPayment(transactionId, paymentMethod)` to set status in SQLite.
  - Call `OrderService.GenerateAccountingEntriesAsync(order, tenantId)` (now public).
  - If `EInvoice_Auto_Export_Enabled` toggle is ON → call `EInvoiceService.SubmitAsync`.
  - Enqueue Outbox event `EInvoiceSynced` with routing key = `ShopInstanceId`; `NatsSyncWorker` publishes `vanan.shoperp.einvoice.synced.{shopInstanceId}`.
  - Idempotent: before creating `JournalEntry`, check `dbContext.JournalEntries.Any(je => je.Reference == orderRef)`.
- **`OrderSyncSubscriber.cs`** — no change (already subscribes to `vanan.cloud.order.created.{shopInstanceId}`).
- **POS `Payment.razor`** — no change. POS calls `ConfirmPaymentAsync` (wrapper) which creates entries locally in SQLite. This is correct: POS = ShopERP, entries belong in SQLite.
  - **Idempotency concern:** if a KhachLink order is also paid via POS (edge case), entries might be created twice. Mitigation: `GenerateAccountingEntriesAsync` checks `JournalEntry.Reference == orderRef` before creating (idempotency guard).

### E-Invoice Service (`3_CoreHub/Services/` or `5_WebApps/ShopERP/Services/`)
- **Existing:** `EInvoiceService` + MISA HTTP client already registered in ShopERP `Program.cs` (line 260-279).
- **No new code needed for e-invoice submission** — `PaymentConfirmedSubscriber` calls existing `EInvoiceService.SubmitAsync`.
- **NEW: sync-back event** — after e-invoice submitted, publish result to NATS for Gateway PG sync.

### NATS Subjects (new)
| Subject | Direction | Publisher | Subscriber |
|---|---|---|---|
| `vanan.cloud.order.payment.confirmed.{shopInstanceId}` | Gateway → ShopERP | Gateway Outbox | ShopERP `PaymentConfirmedSubscriber` |
| `vanan.shoperp.einvoice.synced.{shopInstanceId}` | ShopERP → Gateway | ShopERP `PaymentConfirmedSubscriber` | Gateway `EInvoiceSyncSubscriber` |

  - Idempotency: duplicate message → no double entries.
  - E-invoice toggle OFF → entries created, no e-invoice submission.
- **NEW: `6_Tests/VanAn.Core.Tests/OrderServiceMarkPaidTests.cs`**:
  - `MarkPaidAsync` sets status + enqueues event, does NOT create accounting entries.
  - `ConfirmPaymentAsync` (wrapper) creates entries (backward compat for POS).
- **Manual integration test (Phase 3.5 gate):**

## 3. Detailed Coding Plan

### Implementation Steps

**Step 1 — Split ConfirmPaymentAsync (1 file):**
- `3_CoreHub/Services/OrderService.cs`:
  - Change `GenerateAccountingEntriesAsync` from `private` to `public`.
  - Create `MarkPaidAsync(Guid orderId, Guid tenantId, string transactionId, bool enqueuePaymentConfirmedEvent = false, CancellationToken ct = default)`:
    - Load order, short-circuit if already Paid.
    - Call `order.ConfirmPayment(transactionId, order.PaymentMethod ?? PaymentMethodConstants.Cash)`.
    - Save order.
    - If `enqueuePaymentConfirmedEvent`:
      - Build payload `{ orderId, tenantId, transactionId, paymentMethod, paidAt }`.
      - Enqueue `OutboxEvent(tenantId, ElectronicInvoiceId.Empty, "OrderPaymentConfirmed", json)` with routing key = `ShopInstanceId` (lookup from `Tenant.ShopInstanceId`).
    - If `_orderNotificationService` not null, broadcast `PaymentConfirmed` SignalR.
  - Keep `ConfirmPaymentAsync` as backward-compat wrapper: `MarkPaidAsync(..., enqueuePaymentConfirmedEvent: false)` + `GenerateAccountingEntriesAsync(...)`.
- Build → 0 errors.

**Step 2 — Gateway WebhookController update (1 file):**
- `2_Gateway/Controllers/WebhookController.cs`:
  - Line 160: `ConfirmPaymentAsync` → `MarkPaidAsync`.
  - Update response message.
- Build → 0 errors.

**Step 3 — PaymentConfirmedSubscriber (1 new file):**
- `5_WebApps/ShopERP/Services/PaymentConfirmedSubscriber.cs`:
  - Pattern: same as `OrderSyncSubscriber.cs` (NATS hosted service).

## 6. Approval Gate

**No Domain modification** — only service orchestration changes. `AccountingEntry` immutability preserved.

**Risk: eventual consistency** — accounting entries are delayed by NATS delivery (typically <1s, but can be seconds if ShopERP reconnecting). User-approved: customer sees "Paid" immediately, accounting follows.

**Migration of existing PG accounting entries:** out of scope for this task card. Existing entries in PG stay as historical record. New entries go to SQLite only. If reconciliation needed, separate migration task card.

## 7. Key Design Decisions

| Decision | Rationale |
|---|---|
| `ConfirmPaymentAsync` stays as wrapper | POS Payment.razor backward compat — no UI change needed |
| E-invoice sync back to PG | Gateway admin can view e-invoice status without querying ShopERP |
| Idempotency via JournalEntry.Reference check | Prevents double entries if NATS redelivers or POS + webhook both fire |
| `MarkPaidAsync` enqueues Outbox event | Same transaction as status change — atomic (RC-1 pattern) |
